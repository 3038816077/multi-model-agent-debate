# 性能基线（压测报告）

> 目的：回答「能扛多少并发」这个问题，并区分**服务自身开销**与**上游模型耗时**。

## 环境

| 项 | 值 |
| --- | --- |
| 机器 | Windows 本地（消费级，非服务器） |
| 服务 | 单进程 uvicorn，SQLite 单文件 |
| 压测端 | 同一台机器（会与目标进程抢 CPU，结果偏保守） |
| 限流 | **已关闭**（`RATE_LIMIT_ENABLED=0`），否则测的是限流器 |
| 数据量 | 约 300 个会话 |
| 工具 | `scripts/loadtest.py`（标准库 + requests，无第三方压测框架） |

## 结果

| 接口 | 并发 | RPS | p50 | p95 | p99 | 错误率 |
| --- | --- | --- | --- | --- | --- | --- |
| `GET /health` | 10 | 1068 | 9ms | 13ms | 16ms | 0% |
| `GET /health` | 50 | 1154 | 42ms | 55ms | 66ms | 0% |
| `GET /models` | 10 | 1697 | 6ms | 9ms | 11ms | 0% |
| `GET /models` | 50 | 1658 | 29ms | 49ms | 60ms | 0% |
| `GET /sessions` | 10 | 538 | 18ms | 24ms | 34ms | 0% |
| `GET /sessions` | 50 | 530 | 88ms | 160ms | 256ms | 0% |
| `POST /sessions/archive` | 10 | 496 | 3ms | 38ms | 343ms | 0% |

## 怎么读这些数字

1. **框架层不是瓶颈**：静态接口 `p99` 都在 70ms 以内，50 并发下 RPS 没有明显下降。
2. **`/sessions` 是最重的读接口**（两次查询 + 会话标题聚合），50 并发时 p99 256ms。
   真要优化，先看这里。
3. **写路径的 p99 抖动大**（343ms）：SQLite 写串行 + 每次 `commit` 落盘，属于预期。
   如果要多写并发，需要换 Postgres 或做写入合并。

## 关键结论：真实对话的瓶颈不在服务

一次并行对话的耗时构成：

```
一次请求 ≈ 40 秒
  服务自身      < 100ms
  上游模型调用   ~40s
```

所以「QPS」对这类应用意义有限——**并发上限由供应商限流决定，不是本服务**。
本报告的数字只反映服务自身开销，用于回答「服务会不会先垮」。

## 压测顺手发现的 bug

首轮 `/health` 在并发 10/50 下**错误率 80%/93%**。查下来不是过载，是竞态：

```python
# 修复前：所有请求共用同一个探针文件名
probe = os.path.join(path, ".write_probe")
open(probe, "w").write("ok")
os.remove(probe)      # ← 两个请求互相删掉对方的文件 → FileNotFoundError → 判定目录不可写 → 503
```

改成 `tempfile.NamedTemporaryFile(prefix=".write_probe_", delete=True)` 后：

| | 并发 10 | 并发 50 |
| --- | --- | --- |
| 修复前 | 80.3% 错误 | 93.1% 错误 |
| 修复后 | 0% | 0% |

**这类 bug 单测和手工点都发现不了**：单次请求永远正常，只有并发时才暴露。

## 复现方式

```bash
# 1. 关掉限流起服务
RATE_LIMIT_ENABLED=0 python -m uvicorn app.main:app --port 8000

# 2. 压某个接口
python scripts/loadtest.py --path /sessions --concurrency 50 --duration 15
```

## 没测的部分

- **模型调用链路**：耗时由上游决定（10~60s），压不出有意义的数字
- **多进程/多机**：现在是单进程单机，没有横向扩展
- **长稳测试**：只跑了 12~15 秒的短时压测，没有连续几小时的观察
