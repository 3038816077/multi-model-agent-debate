# 我给多模型并行做了四轮评测，它输给单模型 1.1 分

> **TL;DR**：20 题对照实验，单模型 9.60、并行 8.50，差值 1.10（95% CI [0.60, 1.60]）。
> 差距的来源不是模型更笨——20 题里 17 题被裁判点名「两份答案拼接、有重复」。
> 所以多模型并行的价值不在「更好的答案」，而在「告诉你哪里不一致」。
> 顺带记录三次把评测结论做错的过程，以及 CI 连红三轮的排查。

## 先说这个项目在干什么

不是「让多个模型投票」，而是：

1. 多个模型**独立**回答同一问题（互相看不到）
2. 裁判模型读全部回答，输出结构化 JSON：`共识` / `分歧` / `孤例`
3. **每条分歧必须附逐字引文**，再用代码回查原文

第 3 步是被逼出来的——裁判一开始会编造引文，声称「回答说 X」，但原文根本没这句。

```python
def verify_quote(quote, source, min_chars=10, ratio=0.8):
    q, s = normalize(quote), normalize(source)   # 去标点空白
    if len(q) < min_chars:
        return False
    if q in s:
        return True
    # 允许两成字符被改动（模型引用时常改标点），编造的句子覆盖率会很低
    matched = sum(b.size for b in SequenceMatcher(None, q, s).get_matching_blocks())
    return matched >= ratio * len(q)
```

核对不上的**不丢弃**，降级成「未核实的分歧」——「没核对上」和「没有分歧」是两件事。

## 评测怎么设计的

| 项 | 配置 |
| --- | --- |
| 题集 | 20 题（事实/推理/代码/方案/对比/写作/长文/陷阱） |
| 单模型臂 | Kimi K3 |
| 并行臂 | Kimi K3 + DeepSeek V4 Pro（**包含**单模型臂的模型） |
| 裁判 | GLM-4.6，不在任一臂内 |
| 超时 / 并发 | 240s / 3 |

并行臂刻意做成单模型臂的**严格超集**：同样有 Kimi，额外多一个模型和分歧报告。
这样比较才有意义——否则「并行输」可能只是因为你给它配了弱模型。

## 结果

| 模式 | 均分 | 平均耗时 |
| --- | --- | --- |
| 单模型 | **9.60** | 51s |
| 并行 | **8.50** | 105s |

差值 1.10，95% CI [0.60, 1.60]；并行**赢 3 题、输 17 题**。

## 差距的来源：17/20 题被判「重复」

我把裁判的打分理由逐条看了：

```
q03：内容正确且可执行，但由两份模型回答拼接，有明显重复，根据规则扣 1 分
```

真实产品里用户看到的是**分开的气泡 + 一份分歧报告**，不是两段答案首尾相接。
但评测把并行输出拼成一大段喂给裁判，它当然按「冗余」扣分。

**结论：这个分数测的是「拼接后的文本」，不是「用户读到的东西」。** 想量化并行的价值，得换指标。

## 三次把结论做错（这段最值得看）

### 1. 空输出被当成「没分歧」

首轮跑 22 组分歧评测，kimi 检出率 0%、glm-4.6 准确率 36.4%。看着像模型不行，翻原始输出：

```
kimi     → 输出全是空字符串（思考型模型，max_tokens=800 全被推理吃掉）
glm-4.6  → 22 题里 14 题 429 限流
```

`max_tokens` 改成走注册表、429 加退避重试后：

```
kimi     45.5% → 100%
glm-4.6  36.4%（14 题失败）→ 95.5%（0 失败）
```

### 2. 超时被当成答错

单模型臂 20 题里 6 题得分 0~1，原始回答是：`模型 kimi-k3 请求超时`。90 秒对思考型模型不够。

### 3. 主副模型重复，并行臂 0 秒返回

并行臂每题 0.0 分、耗时 0.0 秒。原因是接口校验「主模型不能和副模型重复」，
而我 `--chief` 和 `--staff` 放了同一个模型，接口直接拒绝，脚本把错误文本当成答案喂给了裁判。

**三次都不是模型问题，是评测脚本问题。** 所以我后来给评分逻辑单独写了 5 个测试——
评分代码错了，比模型错了更可怕。

## 那它到底有什么用

换个问法：**分歧分析本身准不准？**

22 组人工标注（12 组真有冲突、10 组没有），5 个模型分别当裁判：

| 模型 | 准确率 | 检出 | 引文已核实 | 误报 |
| --- | --- | --- | --- | --- |
| Kimi K3.1 Pro | **100%** | 100% | 100% | 0% |
| DeepSeek V4 Flash | 95.5% | 91.7% | 91.7% | 0% |
| GLM-4.6 | 95.5% | 100% | 100% | 10% |
| GLM-4-Flash | 50.0% | 91.7% | 66.7% | **100%** |

两个结论：

1. 强模型做分歧分析已经很可靠（95%~100%，误报 0%）
2. **弱模型绝对不能进阵容**：GLM-4-Flash 把 10 组无冲突样本全编出分歧，误报率 100%

所以定位改成：**决策辅助 / 交叉验证**，而不是「更好的问答」。

## 工程化部分（也踩了不少）

### CI 连红三次，每次原因都不同

```
第一轮  只装了 7 个包，但导入链要 langchain / torch → 一个用例都没跑起来
第二轮  修完依赖，ruff 报 4 个 F821：重构时 return 后面留了段死代码
第三轮  测试数据对不上：CI 用 dummy 注册表，而用例断言「分层里的模型必须在注册表里」
```

现在两个 job 全绿：`test`（lint + 60 个测试，约 30 秒）、`docker-build`。

**关键做法**：单元测试用替身挡掉 torch/faiss/langchain，Docker 构建里执行 `python -c "import app.main"` 做真实依赖冒烟。

### Docker 首次真跑就炸

compose 文件一直有，但没人跑过。第一次跑：

```
OSError: We couldn't connect to '' to load the files,
and couldn't find them in the cached files.
```

容器里连不上 HuggingFace 下载 embedding 模型。改成挂载宿主机缓存（`${HF_CACHE:-./hf_cache}`），
容器 `health=healthy`、`/health` 返回 `models=5, problems=[]`。

### database is locked：真因不是 WAL

踩过两次，一开始以为是 WAL 没开——其实 WAL 早就开了，是**同时起了两个进程**。

修法不是加重试，而是让第二个进程根本起不来：

```python
class InstanceLock:
    def acquire(self):
        handle = open(self.path, 'a+')
        msvcrt.locking(handle.fileno(), msvcrt.LK_NBLCK, 1)   # Windows
        # POSIX 用 fcntl.flock(LOCK_EX | LOCK_NB)
```

进程退出锁自动释放，不会留僵尸锁；顺带补了 `busy_timeout=15000` 和一致性备份
（WAL 下直接 `cp` 数据库文件会丢数据）。

## 三条建议

1. **评测脚本要先自测。** 空输出、429、超时、参数冲突，任何一种都会让结论反向
2. **别用「答案质量」评价多模型系统。** 它的价值在发现分歧，用可读性打分它必输
3. **弱模型进阵容是负收益。** 成本涨、分数降、报告还不可信

---

## 最后

这个项目最初想证明「多模型比单模型强」。四轮评测之后：

**在「直接读一份答案」这件事上它不会更强；在「知道谁在哪里不同意」这件事上，它提供了单模型给不了的信息。**

承认前者，才能把后者做扎实。
