# ADR-0001：单租户，不实现登录与多租户

- 状态：已采纳
- 日期：2026-11-18
- 相关：`app/db/models.py`、`app/middleware/auth.py`

## 背景

项目是一个多模型并行对话系统，当前按「单用户、单机部署」使用。
上线前必然会被问：要不要加登录、要不要做多租户数据隔离。

## 决定

不实现用户登录与多租户隔离。数据模型保持单租户，并在文档中明确写出这条边界。

## 理由

1. **没有真实多用户**：加登录不产生任何可验证的价值，只会增加攻击面。
2. **半成品隔离比没有隔离更危险**：多租户真正的成本不在登录框，
   而在每条查询的归属过滤、配额、数据清理、导出与审计。做一半等于留后门。
3. **边界写清楚同样是工程能力**：能说清「这里为什么不做什么」比堆功能更难。

## 当前的数据边界（事实）

| 数据 | 位置 | 隔离粒度 |
| --- | --- | --- |
| 会话与消息 | `data/agent.db` 的 `sessions` / `messages` | 按 `session_id` 隔离 |
| 跨会话记忆 | `user_memory` 表，固定 `id="global"` | 全局唯一，不隔离 |
| 上传文档 | `data/uploads/<doc_id>.json` | 按 doc_id，会话绑定在 `session_docs.json` |
| 用量与成本 | `data/usage.jsonl` | 全局 |

## 如果要支持多租户，需要改什么

1. 模型层：`sessions` / `messages` / `user_memory` 增加 `owner_id`，所有查询强制带过滤
2. 鉴权：静态 `X-API-Key` → 每用户 token + 过期与轮换；密钥不落前端
3. 配额：按用户统计 token / 成本，超限拒绝（复用 `usage.jsonl` 的记账口径）
4. 数据生命周期：按用户删除与导出，文档与向量库同步清理
5. 迁移：现有 `global` 记忆需要归属到一个默认租户

## 后果

- 部署方必须自己保证「一个实例只服务一个使用者」
- 当前实现不能直接对外提供公共服务（这是有意的）
